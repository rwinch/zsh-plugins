= git-branches-merge-forward

A zsh plugin that merges a chain of branches forward across git worktrees, with strict up-front validation and optional embargoed-branch merging.

== Overview

This plugin automates the "merge forward" workflow of projects that maintain several long-lived version branches (for example `7.0.x` into `main`), including the commercial `embargoed/<role>/<generation>` branches described in link:../../../spring-merge-tutorial[spring-merge-tutorial].
It is worktree-aware: a branch that is checked out in a worktree is merged in that directory, and a branch that is checked out nowhere is checked out in the directory you ran the command from (which goes back to its original branch when the run finishes).
It never pushes. At the end it prints the exact `git push --atomic` commands.

== Features

* The arguments are the whole chain: `git branches-merge-forward 7.0.x 7.1.x main` merges `7.0.x` into `7.1.x`, then `7.1.x` into `main`. The current branch has no special role.
* `--embargoed` treats the arguments as OSS generations and also merges the `embargoed/frozen` and `embargoed/active` branches (down and across)
* `--ours` records across hops with `git merge -s ours`, for branches that carry their own version or dependency updates
* `--feature FEATURE` merges feature branches (`feature/7.0.x/FEATURE`, ...) instead of the branches themselves, so the real branches are never touched
* `--dry-run` validates and prints what would happen, and changes nothing
* It never fetches or pulls: run link:../fetch[git-branches-fetch] and link:../pull[git-branches-pull] first
* Everything is validated before anything changes, and all problems are reported together
* If nothing needs merging it says `Everything is up to date, nothing to merge.` and exits 0
* Conflicts stop at a prompt with the exact commands to resolve them. A merge that fails for another reason prints the error and waits so that you can fix it and retry.

== Installation

[source,bash]
----
antigen bundle rwinch/zsh-plugins git-branches/merge-forward
----

Or manually by adding the plugin directory to your `PATH`.

The plugin also defines the alias `gbbmf` for `git-branches-merge-forward`. See link:../README.adoc#aliases[the group README] for how the `gbb` prefix avoids alias collisions.

To fill in the branches, use the `svaob` alias of link:../../spring-versions[spring-versions] (the OSS branches on one line):

[source,bash]
----
gbbmf $(svaob)
----

`gbbmfa` does that for you, adds `--embargoed` unless you give `--no-embargoed`, and passes any extra options on, for example `gbbmfa --dry-run`.
On a feature branch it also works out the feature and the branches itself, see <<feature-branches,Feature branches>>.

== Usage

[source,bash]
----
git branches-merge-forward [OPTIONS] BRANCH1 BRANCH2 [BRANCH3 ...]
git branches-merge-forward [OPTIONS] --embargoed GENERATION [GENERATION ...]
git branches-merge-forward [OPTIONS] --feature FEATURE BRANCH1 BRANCH2 [BRANCH3 ...]
----

=== Options

[%header,cols="2,1,6"]
|===
| Option | Short | Description

| `--dry-run` | `-n` | Validate and print what would happen. Nothing is changed, and it exits 0.
| `--allow-ahead` | `-a` | Let any branch in the chain be ahead of its upstream. Behind and diverged still fail. Useful when resuming an aborted run, and when several branches carry their own unpushed commits.
| `--ours` | `-o` | Record across hops with `git merge -s ours` (nothing is carried, so there are no conflicts). Down hops stay real merges.
| `--embargoed` | `-e` | The arguments are OSS generation branches, oldest to newest. One generation is enough.
| `--feature FEATURE` | `-f` | Merge feature branches instead of the branches. `feature/<branch>/FEATURE` is created from every branch, and the chain is merged between them. See <<feature-branches,Feature branches>>.
| `--fork-remote REMOTE` | | With `--feature`: the remote the feature branches of non-embargoed branches are pushed to. Default: your GitHub login (from `gh api user`), the name `git-clone-convention` gives your fork.
| `--pause` | `-P` | After each merge, stop so that the result can be validated, and say which directory to do it in.
| `--help` | `-h` | Display the help message.
|===

== Validation

Nothing changes until all of this passes. Problems are collected and reported together.

. Every branch exists locally (it is never created for you)
. Every branch has an upstream, and the upstream still exists on the remote
. Every worktree that will be touched is clean (untracked files count), and has no merge, rebase or cherry-pick in progress
. Every branch equals its upstream, as of the last fetch (nothing is fetched, see link:../fetch[git-branches-fetch]). The *first* branch may be ahead of its upstream, because that is the work you are merging forward. Behind and diverged always fail. With `--allow-ahead` any branch may be ahead.

A missing upstream is reported with the command that sets it (`git branch --set-upstream-to=<remote>/<branch> <branch>`).
Each branch is compared with its *own* upstream, so there is no `--remote` option.

== Merging across worktrees

* A branch checked out in another worktree is merged in that worktree. This never fails because of it.
* A branch that is checked out nowhere is checked out in the directory you ran the command from.
* After a normal finish that directory is switched back to its original branch. After an abort or an error nothing is restored: the message says which branch the directory was on.

== Embargoed branches

With `--embargoed` every argument is a generation and the plan follows the "How an OSS contribution is merged" section of the tutorial.

[source,text]
----
$ git branches-merge-forward --dry-run --embargoed 7.0.x main
Plan:
  (1) 7.0.x                   -> main                     across merge would merge
        dir: /code/spring-merge   upstream: oss/main
  (2) 7.0.x                   -> embargoed/frozen/7.0.x  down   merge would merge
  (3) main                    -> embargoed/frozen/main   down   merge would merge
  (4) embargoed/frozen/7.0.x -> embargoed/frozen/main   across merge would merge
  (5) embargoed/frozen/7.0.x -> embargoed/active/7.0.x  down   merge would merge
  (6) embargoed/frozen/main  -> embargoed/active/main   down   merge would merge
  (7) embargoed/active/7.0.x -> embargoed/active/main   across merge would merge

Dry run: nothing was changed. At the end it would print:
  git push --atomic oss \
    7.0.x main
  git push --atomic commercial \
    embargoed/frozen/7.0.x embargoed/frozen/main embargoed/active/7.0.x embargoed/active/main
----

For every generation (`N`) the plan is: the OSS branches merge across, then for `frozen` and then `active` each `embargoed/<role>/<generation>` merges down (the OSS branch into `frozen`, `frozen` into `active`) and across (the same embargoed branch of the previous generation).
In a dry run a hop is `up to date` when its source is already in its target, and `would merge` otherwise. Hops that depend on an earlier merge are shown as `would merge`.

The CVE flow of the tutorial needs no option: `git branches-merge-forward embargoed/active/7.0.x embargoed/active/main` is a plain chain.

== Dependency updates (`--ours`)

When each branch carries its own version or dependency updates that must not merge into the next branch, use `--ours`.
Across hops run `git merge -s ours --no-ff -m "merge(ours): <source> into <target>"`: the merge is recorded but nothing is carried, so there are no conflicts.
Down hops stay real merges, so every generation keeps its own updates in its embargoed branches.

Merge messages that involve embargoed branches name the generation branches instead, so history never mentions `embargoed/<role>/`: `Merge branch '7.1.x' into '7.1.x'` for a down hop, `merge(ours): 7.0.x into 7.1.x` for an ours across hop.

If `7.0.x`, `7.1.x` and `main` each carry their own unpushed dependency updates:

[source,bash]
----
git branches-merge-forward --ours --allow-ahead --embargoed 7.0.x 7.1.x main
----

`--allow-ahead` is needed because `7.1.x` and `main` are ahead of their upstreams. Drop it if those updates are already pushed.

== Feature branches (`--feature`)

To merge a fix forward without touching the real branches, use a feature branch per branch:

[source,bash]
----
git branches-merge-forward --feature bug1 7.0.x 7.1.x main
----

For every branch in the chain this creates `feature/<branch>/bug1` from the branch (`feature/7.0.x/bug1` from `7.0.x`, ...), and then merges them forward as usual: the first feature branch is into `feature/7.1.x/bug1`, and so on.
The first branch is only created, nothing is merged into it, so it is where your fix goes if you are not on it yet.

Embargoed branches get the same name with the whole branch in the middle (`embargoed/frozen/7.0.x` becomes `feature/embargoed/frozen/7.0.x/bug1`), so `--embargoed` works too.
The name is `feature/<branch>/FEATURE` and not `<branch>/FEATURE` because git cannot have a branch `7.0.x` and a branch `7.0.x/bug1` at the same time.
`FEATURE` may not contain a `/`.

[source,text]
----
$ git branches-merge-forward --dry-run --feature bug1 7.0.x main
Feature branches (created from their base, no upstream until pushed):
  feature/7.0.x/bug1  from 7.0.x
  feature/main/bug1   from main

Plan:
  (1) feature/7.0.x/bug1 -> feature/main/bug1  across merge would merge
        dir: /code/spring/main   base upstream: oss/main

Dry run: nothing was changed. At the end it would print:
  git push --atomic -u rwinch \
    feature/7.0.x/bug1 feature/main/bug1
----

* *Where they are created.* Each feature branch is created in the worktree of its branch (or in the directory you ran from when the branch is checked out nowhere). The worktrees of the branches stay on the feature branches, and the end of the run lists them (`gwws` switches them all back at once). The directory you ran from is switched back, as usual.
* *Starting on the first feature branch.* If you are already on `feature/7.0.x/bug1` it is the start: it is not created again, and the work on it is what gets merged forward. Any other feature branch that already exists is a problem.
* *Merge messages.* They use the branch names, `Merge branch '7.0.x' into 'main'`, never the feature names.
* *Upstreams.* The feature branches are created without an upstream. The push commands that are printed use `-u`, so the upstream is the remote you push to: your fork for non-embargoed branches (`--fork-remote`, by default your GitHub login), and the upstream remote of the branch (`commercial`) for the embargoed ones. Nothing is pushed.
* *Validation.* The branches are validated as usual (clean worktrees, up to date with their upstreams). The first branch may be ahead, and the feature branches then carry those commits. A feature branch whose name is taken, or collides with a branch that is also a directory in the name (a branch called `feature`), is reported with the other problems.
* `--ours`, `--pause` and `--dry-run` work as before.

=== `gbbmfa` on a feature branch

`gbbmfa` works out the feature and the chain from the branch you are on. On `feature/7.0.x/bug1` it runs the OSS branches from `7.0.x` onwards (with the embargoed ones, unless `--no-embargoed`) with `--feature bug1`:

[source,bash]
----
git switch feature/7.0.x/bug1
gbbmfa            # same as: gbbmf --feature bug1 --embargoed 7.0.x 7.1.x main
----

On `feature/7.1.x/bug1` it starts at `7.1.x`, so `7.0.x` and its embargoed branches are left out.
`gbbmfa --feature NAME` (or `-f NAME`) wins over the name of the branch you are on: the chain is only cut when `NAME` is the name of the current branch, and otherwise the full list is used.
If the branch in the middle is not an OSS branch (an embargoed one, for example) nothing is inferred, and `gbbmf` with the branches is the way to go.
`gbbmf` itself never infers anything from the current branch.

== Release branches

Rebuilding `release/<version>` branches is done by link:../release[git-branches-release]. Run it after the merged branches are pushed.

== The end of a run

[source,text]
----
Done! Merged 7 hop(s).
Restored '7.0.x' in /code/spring-merge

Nothing has been pushed. To publish, run:
  git push --atomic oss \
    7.0.x main
  git push --atomic commercial \
    embargoed/frozen/7.0.x embargoed/frozen/main embargoed/active/7.0.x embargoed/active/main
----

There is one command per remote, in plan order, because `--atomic` cannot span remotes.
A branch whose upstream has a different name is pushed as `local:remote-name`.

== Examples

[source,bash]
----
# merge 7.0.x into 7.1.x, then 7.1.x into main
git branches-merge-forward 7.0.x 7.1.x main

# see what would happen
git branches-merge-forward --dry-run 7.0.x main

# fetch and fast-forward every branch first
git branches-fetch 7.0.x main && git branches-pull 7.0.x main

# resume after an aborted run (the merged branches are ahead of their upstreams)
git branches-merge-forward --allow-ahead 7.0.x main

# merge, including the embargoed branches
git branches-merge-forward --embargoed 7.0.x main

# short options
git branches-merge-forward -n -d 7.0.x main

# merge a fix on feature/7.0.x/bug1 forward through feature branches
git branches-merge-forward --feature bug1 7.0.x 7.1.x main
----

== Tests

`test/test.sh` builds throwaway repositories (bare `oss` and `commercial` remotes, worktrees and embargoed branches) and checks the behavior above:

[source,bash]
----
git-branches/merge-forward/test/test.sh            # all tests
git-branches/merge-forward/test/test.sh ours       # tests whose name contains "ours"
DEBUG=1 git-branches/merge-forward/test/test.sh    # also print the output of every run
----

== Requirements

* Must be run from within a git repository (not a bare one)
* Every branch needs an upstream
* Every worktree touched must be clean, including untracked files
* Git worktree support (Git 2.5+)
